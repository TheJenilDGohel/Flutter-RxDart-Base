## The one rule that matters: where does state live?

**"Does this data need to survive navigation or a cold app restart?"**

- **YES → `AppStore` (Redux)** — auth token, user profile, locale. Nothing else goes here.
- **NO → Feature BLoC (RxDart)** — API fetch state, form fields, UI toggles. This is almost
  everything you'll touch day to day.

If you're unsure which side a piece of state belongs on, say so and ask — don't guess and
don't put screen-local state in Redux "to be safe."

## Adding a feature (daily workflow)
1. `dart run scripts/agent/wire_route.dart <feature_name>` — scaffolds via `mason make bloc`
   if missing, then wires the route into `routes.dart` / `app_router.dart`.
2. Fill in repo → bloc → model → widgets/page following the golden rules.
3. Run `scripts/agent/verify.ps1` (Win) or `./scripts/agent/verify.sh` (Mac/Linux) before commit.

## Hard rules (see AGENTS.md for the full 12)
- Repository is transport ONLY — call `ApiBaseHelper`, return raw `Map`, never `Model.fromJson`.
- BLoC owns business logic — parse with `Model.fromJson`, emit `ApiResponse<T>`.
- Zero `setState` in widgets — use stream builders.
- Zero RxDart outside BLoC — widgets consume plain `Stream<T>` / `ApiResponse<T>` only.
- Rules #1, #3, #4 are **analyzer-enforced** by `redux_rxdart_lints` custom_lint plugin.
- Never hardcode pixel sizes — use ScreenUtil `.w` `.h` `.r` `.sp`.
- Errors reach UI only through `exception.userFacingMessage`.

## Cost/mode defaults
Routine feature work is a single-session, single-agent job — don't spin up agent teams or
background subagents. Don't switch to Opus unless genuinely stuck on something hard. If you
want a QA review of a finished feature, invoke the `flutter-qa` agent explicitly.
